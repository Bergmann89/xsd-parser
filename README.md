# Overview

This library is built around a staged transformation pipeline that converts XML schemas into Rust source code. Each stage handles a specific level of abstraction and produces a well-defined intermediate representation. This makes the library highly flexible, testable, and suitable for advanced customization or tooling.

![overview](./doc/overview.svg "Overview")

## Pipeline Stages

1. **Parsing:**
   The parsing stage is handled by the `Parser` type. It loads XML schemas from files or URLs and uses pluggable `Resolver`s to fetch and preprocess schema definitions. The result is captured in a `Schemas` model, which stores namespaces, prefixes, and the raw schema structure needed for further processing.

2. **Interpreting:**:
   Interpreting is carried out by the `Interpreter`. This stage analyzes the schema definitions stored in the `Schemas` model and converts them into normalized, abstract type descriptions. The resulting `MetaTypes` model encapsulates schema semantics such as complex types, enumerations, references, and groups in a language-agnostic form.

3. **Optimizing:**
   Optimization is performed by the `Optimizer`, which takes the `MetaTypes` and applies structural transformations. These include deduplication, simplification of unions, merging cardinalities, and resolving typedef aliases. The goal is to prepare the type graph for idiomatic translation into Rust while reducing complexity.

4. **Generating:**
   The generation step uses the `Generator` to transform the abstract types into Rust-specific type data. It produces the `DataTypes` model by attaching names, Rust derivations, trait support, and rendering metadata. These enriched types form the basis for later rendering while still preserving schema semantics.

5. **Rendering:**
   Rendering is handled by the `Renderer`, which converts `DataTypes` into structured Rust code organized in a `Module`. It uses the `RenderStep` trait to define individual rendering steps. Several built-in steps are available, including support for `serde` or `quick-xml`. Users can also add custom `RenderStep` implementations to extend or modify the output.

## Data Models

- **`Schemas`:**
  This model is built by the `Parser` and contains the raw XML schema data, including namespaces, prefixes, and schema file content. It serves as the foundation for interpretation and supports multiple sources and resolver types.

- **`MetaTypes`:**
  Generated by the `Interpreter`, this model contains language-neutral type definitions. It includes data like complex types, references, enumerations, and groupings derived from schema structure. It is suitable for introspection, transformation, and optimization.

- **`DataTypes`:**
  Produced by the `Generator`, this model holds enriched Rust-specific type data. Each type includes metadata for layout, naming, derivations, and other traits required for rendering idiomatic Rust code. This is the core input for the rendering process.

- **`Module`:**
  The final model is produced by the `Renderer`. It wraps the Rust source code output into a structured format, ready for file output or consumption as token streams. Modules support nested submodules, file splitting, and embedded metadata for customization.


# Features

This library provides the following features:

- **Rust Code Generation:** Convert any XML schema into Rust code.
- **Layered Architecture:** Add user-defined code to manipulate type information or generated code.
- **User-Defined Types:** Inject existing types into the generated code to reuse predefined structures.
- **`serde` Support:** Generate code for serialization and deserialization using [`serde`](https://docs.rs/serde) with [`serde_xml`](https://docs.rs/serde-xml-rs) or [`quick_xml`](https://docs.rs/quick-xml) as serializer/deserializer.
- **`quick_xml` Support:** Direct serialization/deserialization support using [`quick_xml`](https://docs.rs/quick-xml), avoiding `serde` limitations and leveraging asynchronous features. Code generated for very large schemas may need a higher `#![recursion_limit]` (e.g. `256`) in the crate that includes it.


# Getting Started

The usual setup generates the code in the build script of your crate. Add `xsd-parser` as build dependency and `xsd-parser-types` (with the features your generated code needs, e.g. `quick-xml`) as normal dependency:

```toml
[dependencies]
xsd-parser-types = { version = "0.3", features = ["quick-xml"] }

[build-dependencies]
xsd-parser = "1.6"
```

Then generate the code in `build.rs` and include it from your crate:

```rust,no_run
use std::{env, fs, path::PathBuf};

use xsd_parser::{config::Schema, generate, Config, Error};

fn main() -> Result<(), Error> {
    let config = Config::default()
        .with_schema(Schema::File("schema/my-schema.xsd".into()))
        .with_quick_xml();

    let code = generate(config)?;

    let out_dir = PathBuf::from(env::var("OUT_DIR").unwrap());
    fs::write(out_dir.join("my_schema.rs"), code.to_string())?;

    Ok(())
}
```

```rust,ignore
// src/lib.rs
pub mod my_schema {
    include!(concat!(env!("OUT_DIR"), "/my_schema.rs"));
}
```

The examples in [`xsd-parser/examples`](https://github.com/Bergmann89/xsd-parser/tree/master/xsd-parser/examples) and [`examples`](https://github.com/Bergmann89/xsd-parser/tree/master/examples) show more advanced setups, and the feature tests in [`xsd-parser/tests/feature`](https://github.com/Bergmann89/xsd-parser/tree/master/xsd-parser/tests/feature) contain a small schema, the used `Config` and the generated code for almost every feature.

## Common Pitfalls

- **`GeneratorFlags::all()` includes `ADVANCED_ENUMS`:** Advanced enums need the `RenderStep::EnumConstants` render step, otherwise the generated code does not compile (`VALUE_*` constants are missing). Either use `Config::with_advanced_enums`, which adds both, or remove the flag (`GeneratorFlags::all() - GeneratorFlags::ADVANCED_ENUMS`).
- **`InterpreterFlags::all()` includes `WITH_NUM_BIG_INT`:** Unbounded XSD integer types are then generated as `num::BigInt` / `num::BigUint`. Add `num` to your dependencies and enable the `num` feature of `xsd-parser-types` if the types are (de)serialized with `quick-xml`.
- **Features of `xsd-parser-types` must match the render steps:** Code generated with `quick-xml` support needs the `quick-xml` feature (and `async` for the async reader), `serde` support needs the `serde` feature, and the decoding types of `Config::with_base64binary_type` need the `base64` feature.
- **Documents that are not UTF-8:** The `IoReader` and `SliceReader` only accept UTF-8. Use the `DecodingIoReader` of `xsd-parser-types` to read other encodings (detected from the BOM or the XML declaration, sync only), and the `EncodingWriter` to write them. Its `write_document` method writes the value as complete document with a matching XML declaration (the serializers themselves never write a declaration).
- **Unknown elements are rejected by default:** The `quick-xml` deserializer fails on elements that are not part of the schema. Use the `skip_unknown_elements` option of `RenderStep::QuickXmlDeserialize` (or `Config::with_quick_xml_config`) to skip them.
- **Dynamic types without `abstract`:** Types that are only used through `xsi:type` but are not declared as `abstract` must be marked with `Config::with_dynamic_type`, otherwise the derived types are not taken into account.
- **Name conflicts:** If two schema types end up with the same Rust name, the generator returns a `DuplicateTypeName` error. Enable `GeneratorFlags::USE_MODULES` (one module per namespace) or assign custom names (see the `custom_names` and `custom_naming` examples).
- **Very large schemas:** The generated code for large schemas may need a higher `#![recursion_limit]` (e.g. `256`) in the crate that includes it.

# Changelog

Below you can find a short list of the most important changes for each released version.

## xsd-parser-types 0.3.1

- **Reading and Writing Other Encodings**
  `xsd-parser-types` 0.3.1 adds the `DecodingIoReader`, which decodes the input based on the BOM or the XML declaration (e.g. `Windows-1251` or `UTF-16`), and the `EncodingWriter`, which encodes the serialized output (`write_document` writes a complete document including the matching XML declaration). Characters that can not be represented in the target encoding are written as numeric character references in text and attribute values. Since the upgrade to `quick-xml` 0.42 the `IoReader` only accepts UTF-8.

## Version 1.6.0

This release adds proper support for dynamic and abstract types, opt-in skipping of unknown elements and dedicated types for binary data. It also upgrades `quick-xml` to 0.42 and fixes a long list of issues found with real-world schemas. Because `xsd-parser-types` re-exports `quick-xml` types, it gets a new minor version (`0.3.0`). Please have a look at the breaking changes at the end of this section before upgrading.

- **Proper Support for Dynamic and Abstract Types**
  Abstract complex types and types configured as dynamic (`Config::with_dynamic_type`) are now generated as dynamic types, also in combination with substitution groups. The concrete types of a substitution group or a dynamic type use a separate postfix (`Dyn` by default, see `Config::with_dynamic_element_postfix`). The new optimizer flag `MERGE_DYNAMIC_TYPES` stores substitution group members and derived types of the same element in one dynamic type.

- **Opt-In Skipping of Unknown Elements**
  The `quick_xml` deserializer can now skip unknown elements including their whole subtree. The option is enabled with the new `skip_unknown_elements` field of `RenderStep::QuickXmlDeserialize` (or the new parameter of `Config::with_quick_xml_deserialize_config` and `Config::with_quick_xml_config`). Known elements at an unexpected position still fail. Without the option the generated code is unchanged and unknown elements are rejected.

- **Types for `base64` and `hex` Encoded Data**
  `xs:base64Binary` and `xs:hexBinary` are now mapped to the new `Base64String` and `HexString` types of `xsd-parser-types`, which keep the encoded value, instead of `String`. Length facets are now checked against the decoded data instead of the encoded string. The decoding variants `Base64Binary` and `HexBinary` can be used with `Config::with_base64binary_type` and `Config::with_hexbinary_type`.

- **Upgrade to `quick-xml` 0.42**
  `quick-xml` was upgraded from 0.38 to 0.42 (including the fixes for the RustSec DoS advisories of older versions). The byte-based API of `xsd-parser-types` stays as it is, the changes are handled at the `quick-xml` boundary. Input that is not valid UTF-8 is now rejected with an encoding error. The required toolchain was raised to Rust 1.95 and all other dependencies were updated to their latest versions.

- **Custom Generator Code**
  Custom types (`CustomMeta`) can carry a `CustomGenerator` that is executed when the generator processes the type, for example to generate dependent types or to resolve type paths.

- **Helper Functions for Flattened Content**
  The new `RenderStep::ContentHelpers` generates accessor methods for structs with flattened content (e.g. `fn private_note(&self) -> Option<&String>`).

- **Shared Content Types**
  Complex types that use the same content (e.g. through the same `xs:group`) now share one generated content type instead of getting a copy per owner.

- **Configurable Name for Content Fields**
  The name of the generated content field can be changed with `Config::with_content_display_name`, to avoid conflicts with schema attributes or elements called `content`.

- **Better Error Reporting**
  - The interpreter returns errors instead of panicking for types that are missing or not generated yet, and `InterpreterError::NoType` names the affected type
  - The generator returns the new `Error::DuplicateTypeName` if two schema types would be generated with the same name, instead of producing code that does not compile
  - Invalid user provided identifier paths (derives, includes of custom types) return errors instead of panicking
  - File resolver and parser errors now contain the affected file path (`FileResolverError`, `InvalidFilePath`)

- **Additional Bug Fixes**
  - Fixed a panic for derived types that are declared before their base type
  - Fixed a panic in the interpreter for multiple schemas without `RESOLVE_INCLUDES`
  - Fixed `xs:pattern` facets of different derivation steps, they are now combined with AND as required by the XSD specification
  - Fixed substitution group members without a type, they now use the type of their head instead of `xs:anyType`
  - Fixed global attributes without a type, they now use `xs:string` like local attributes
  - Fixed `quick_xml` (de)serialization of newtypes of complex types (`TypedefMode::NewType`)
  - Fixed default values of `xs:element` for simple content types (e.g. extensions of `xs:boolean`)
  - Fixed `quick_xml` deserialization of choices with a group variant followed by an unexpected element, and of mixed choices with leading text
  - Fixed the trait implementation of dynamic types for derived types that are generated before their base
  - Fixed boxing of recursive types through shared content types
  - Fixed `USE_UNRESTRICTED_BASE_TYPE_COMPLEX` for types that restrict an abstract base type
  - Fixed `xmlns` emission for schemas with unqualified elements
  - Fixed `GENERATE_PREFIXES` not assigning the generated prefix to the namespace
  - Fixed the `Default` implementation of defaultable choices with a single option
  - Fixed render steps being added twice by the config helpers
  - `xs:documentation` entries are now rendered as separate paragraphs, and documentation with CRLF line endings is unindented correctly
  - `xsd-parser-types` can be built with the `xml` feature but without `quick-xml`

- **Breaking Changes**
  - `xsd-parser-types` 0.3.0: `quick-xml` types in the public API changed with the upgrade to 0.42. `read_attrib` takes the attribute value as `&str`, the dynamic type name helpers return `Cow<str>`, and `Key::qname`, `Key::prefix_decl`, `Value::namespace` and `Element::qname` return a `Result`.
  - Input that is not valid UTF-8 is rejected by the `quick_xml` deserializer.
  - Building requires a newer compiler, the pinned toolchain was raised from Rust 1.86 to 1.95.
  - `RenderStep::QuickXmlDeserialize` has the new `skip_unknown_elements` field, and `Config::with_quick_xml_deserialize_config` and `Config::with_quick_xml_config` take an additional parameter.
  - `Constrains::patterns` is grouped per derivation step (`Vec<Vec<String>>`), and the generated pattern validation is stricter.
  - `InterpreterError::NoType` carries the identifier of the affected type, and the generator error has the new variant `DuplicateTypeName`.
  - The generated code changes for several schemas: abstract types are generated as dynamic types, content types may be shared between complex types, `xs:base64Binary` and `xs:hexBinary` use the new types, and substitution group members without a type use the type of their head.

## Version 1.5.0

This release introduces several new schema features, a refactored identifier system, improved deserialization, and a range of bug fixes targeting real-world XSD compatibility.

- **Support for `xs:anySimpleType`**
  `xs:anySimpleType` is now handled as a distinct type instead of being silently mapped to `xs:string`. A new `AnySimpleType` runtime type was added to `xsd-parser-types`, and the generator can be configured to use any custom type in its place.

- **Support for `xs:redefine` and `xs:override`**
  The parser and interpreter now support the `xs:redefine` and `xs:override` schema composition mechanisms, enabling proper handling of schemas that redefine or override type definitions from imported schema files.

- **Namespace-Aware Enum Serialization and Deserialization**
  Enum values that carry namespace-prefixed content (e.g., `tns:Sender`) are now correctly serialized and deserialized by resolving the namespace URI at runtime rather than comparing literal prefix strings. This fixes incorrect behavior for enums derived from `xs:QName`-like patterns.

- **Support for Duplicated Type Identifiers Across Schema Files**
  The identifier system was restructured to distinguish between types from different schema files. The previous `Ident` type was split into `TypeIdent`, `NodeIdent`, and `PropertyIdent`. `TypeIdent` now carries a `SchemaId`, enabling correct resolution of types that share a name across multiple schema files.

- **`DerivedTypeMeta` for Naming Conflict Resolution**
  A new `DerivedTypeMeta` structure tracks derived types and their display names within `DynamicMeta`. This resolves naming conflicts that occurred when multiple derived types shared the same name across different schemas (e.g., AIXM schema).

- **Support for Non-Zero Integer Types**
  Integer types with matching XSD constraints can now be mapped to Rust's `NonZero*` types (e.g., `NonZeroU8`, `NonZeroI32`). This is independent of the `WITH_NUM_BIG_INT` feature and can be enabled via generator configuration.

- **Improved Name Generation**
  The `Naming` trait and its built-in implementations were improved to handle more edge cases, including duplicate group names and nested types that previously caused naming collisions in generated code.

- **Anchored Regex Pattern Validation**
  Pattern facets (`xs:pattern`) are now correctly anchored at the start and end (`^...$`) as required by the XSD specification. Additionally, patterns with alternation are wrapped in a non-capturing group to prevent partial anchoring issues.

- **Improved `quick_xml` Deserialization**
  The `quick_xml` deserializer received a comprehensive overhaul, improving correctness for complex schema patterns such as dynamic types, mixed content, and deeply nested structures.

- **New Examples and Benchmarks**
  - Added a `BPMN 2.0` example project
  - Added a `VSME` schema example project
  - Added memory usage and performance benchmarks to the `benchmark` crate

- **Additional Bug Fixes**
  - Fixed edge case in `quick_xml` deserialization of simple list types
  - Fixed namespace serialization for the `Element` type
  - Fixed list deserialization when using non-whitespace separators
  - Fixed invalid character escaping when deserializing XML attributes
  - Fixed naming collision for group types reused across inheritance hierarchies
  - Fixed `WithNamespaceTrait` generating conflicting implementations for type aliases
  - Fixed empty list handling (previously reported as an error)
  - Fixed a typo in the `with_element_type_postfix` setter method

  Both `GeneratorFlags::BUILD_IN_ABSOLUTE_PATHS` and the new `GeneratorFlags::ABSOLUTE_PATHS_INSTEAD_USINGS` flag now ensure that all built-in types and traits are resolved using absolute paths, reducing the risk of naming conflicts.

- **Additional improvements include**
  - faster loop detection for large schemas resulting in better performance while code generation
  - improved namespace handling and prefix resolution

## Version 1.2

This release introduces a series of architectural improvements, enhanced flexibility in code generation, and broader schema compatibility.

- **Refactored Pipeline Structure**
  The internal code generation pipeline has been refactored to introduce a new `Renderer` step and an accompanying `DataType` model. This separation gives users more control over the rendering process, allows better extension points for customization, and prepares the architecture for further growth.

- **Refactored Serde Support**
  Support for `serde` has been moved into dedicated renderer steps. This makes it possible to support multiple versions of `serde`-based implementations, such as `serde-xml-rs` 0.7 and 0.8, without mixing code. Each renderer step now cleanly encapsulates the logic for one serialization backend.

- **Implement Support for Unstructured Data**
  Added support for `xs:any` and `xs:anyAttribute` by introducing an internal representation for unstructured XML data. This enables working with flexible or unknown schema elements and fixes a long-standing gap in schema coverage.

- **Implement Support for `BigInt` and `BigUint`**
  Schemas defining integer types without upper bounds can now be mapped to `num::BigInt` or `num::BigUint`, depending on context. This is useful when working with large numeric values.

- **Improved Documentation Support**
  XSD annotations (`xs:documentation`) are now parsed and included as Rust doc comments in the generated code, improving type-level visibility and usability.

- **Different Bug Fixes and Improvements**
  - Enum restrictions on text types are now correctly interpreted and rendered
  - Complex types in the XML Catalog schema are now rendered correctly
  - Introduced per-type `derive` settings for advanced customization
  - Various naming, escaping, and formatting issues were resolved across the pipeline.
  - Generated names of nested elements now uses the name of the parent element as prefix to prevent name collisions.
