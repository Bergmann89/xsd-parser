# Notes for AI Coding Agents

This file is for AI tools that work on the `xsd-parser` repository itself. [`CONTRIBUTING.md`](CONTRIBUTING.md) is the main guide (layout, tests, checks, code style, commits) and applies to agents as well. The points below are the ones agents get wrong most often.

If you only use `xsd-parser` in another project, the "Getting Started" and "Common Pitfalls" sections of the [`README.md`](README.md) are the relevant part.

## Tests and Snapshots

- Never run `cargo test --all-features` on the workspace. It enables the `update-expectations` feature, which overwrites the expected files instead of checking them.
- Never edit files in `tests/**/expected/` by hand. Regenerate them with `cargo test -p xsd-parser --features update-expectations <filter>` (add `,base64` for the tests that need it), then run the tests again without the feature and review the snapshot diff. Every changed snapshot must be explained by the change.
- A bug fix needs a test that fails without the fix with a failing assertion, not with a compile error. New tests go into `xsd-parser/tests/feature/<name>/` and are registered in `xsd-parser/tests/feature/mod.rs`.
- Feature tests that read XML must be guarded with `#[cfg(not(feature = "update-expectations"))]`, see the existing tests.
- The test files must have LF line endings. A schema that intentionally uses CRLF needs a `-text` entry in `.gitattributes`.

## Checks

Run all checks from [`CONTRIBUTING.md`](CONTRIBUTING.md#checks) before you report a change as done. Clippy runs with `--deny warnings` and the pedantic lints of the workspace, also for test code. The `benchmark` crate is not a default workspace member, so check it explicitly when the generated code or `xsd-parser-types` changes.

## Generated Code

- `xsd-parser/src/models/schema/xs_generated.rs` is generated by the `update_schema` example (`cd xsd-parser && cargo run --example update_schema`, then format it with `rustfmt` and replace the file). Do not edit it by hand.
- Changes to the renderer change the generated code of many tests at once. Check a few changed snapshots in detail instead of only counting them.

## Code

- Do not add `unwrap`, `expect` or `panic!` for conditions that depend on the schema or the user configuration. Return an error.
- Keep public APIs stable unless the task is about changing them. Breaking changes must be mentioned in the pull request.
- Prefer existing helpers and patterns of the surrounding code over new abstractions.

## Commits

- Conventional Commits (`fix(renderer): ...`), the body explains why.
- No issue or pull request references in commit messages, they belong into the pull request description.
- Never commit the `examples/read_write/output.xml` change produced by running the example.
